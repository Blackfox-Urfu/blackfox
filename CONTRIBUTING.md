Операции с файлами и каталогами являются основными при работе с операционной системой Linux. Ниже приведены часто используемые команды для работы с файлами и каталогами:

| Команда | Описание | Опции | Примеры |
| ------- | -------- | ----- | ------- |

### 1. Настройка репозитория и структуры проекта
1. **Настройка веток**: обычно используется основная ветка (например, `main` или `master`) для стабильной версии проекта и дополнительные ветки для разработки.
2. **Описание проекта**:  `README.md` состоит из описания проекта, а также `CONTRIBUTING.md` с правилами участия. Укажите, как вносить изменения, добавлять новых участников и предлагать задачи.


### 2. Управление версиями (Version Control)
1. **Создание веток**: рекомендуется для каждой новой задачи или исправления ошибки создавать отдельные ветки (например, `feature/add-auth`, `bugfix/fix-login`). Это помогает изолировать изменения и позволяет легче отслеживать прогресс по каждой задаче.
   - Команда: `git checkout -b <branch-name>` для создания новой ветки.

2. **Коммиты**: придерживайтесь понятного и единого стиля коммитов (например, с указанием типа изменений: `feat`, `fix`, `docs`). Это поможет вести историю изменений чистой и понятной, упростит навигацию по истории изменений.
   - Команда: `git commit -m "type: описание изменений"` для создания коммита с пояснением.

3. **Pull Request (PR)**: перед слиянием ветки с основной создайте pull request. Это позволяет другим участникам проверить код, обсудить изменения и выявить возможные проблемы до их включения в основную ветку.
   - Команды:
     - `git push origin <branch-name>` для отправки изменений в удаленный репозиторий.
     - `gh pr create` для создания pull request через GitHub CLI.

4. **Code Review**: обязательная проверка кода перед слиянием помогает поддерживать качество и стабильность кода, предотвращая ошибки.
   - Команда: `gh pr review <pull-request-id> -r` для проведения code review через GitHub CLI.

5. **Слияние веток**: после успешного code review и прохождения всех тестов, ветку можно сливать с основной. Обычно для этого используются следующие подходы:
   - **Merge commit**: создает отдельный коммит слияния, что позволяет сохранить историю изменений ветки.
     - Команда: `gh pr merge <pull-request-id> --merge`
   - **Squash and merge**: объединяет все коммиты ветки в один, что делает историю основной ветки чище и легче для восприятия.
     - Команда: `gh pr merge <pull-request-id> --squash`
   - **Rebase and merge**: выполняет слияние, сохраняя коммиты, но размещая их поверх основной ветки, избегая коммита слияния. Это помогает сохранить историю изменений линейной, но может усложнить процесс при наличии конфликтов.
     - Команда: `gh pr merge <pull-request-id> --rebase`

### 3. Планирование и организация задач
1. **GitHub Projects и Issues**:
   - Используйте **Issues** для создания задач, багов и обсуждений. Каждую задачу можно назначать участникам, добавлять метки (labels) и определять приоритет.
   - В **GitHub Projects** можно создать канбан-доску для управления задачами, организовать задачи по статусу (например, `To Do`, `In Progress`, `Done`).
2. **Milestones**: создавайте этапы проекта (milestones), чтобы разбить его на конкретные цели. Привязывайте задачи к milestone, чтобы отслеживать прогресс по каждой цели.
3. **План спринтов**: если работаете по Agile, можно определить спринты, в каждом из которых будут свои задачи и цели. Используйте Project Board для планирования задач в каждом спринте.

### 4. Управление доступом и ролями
1. **Приглашение участников**: пригласите участников в репозиторий и настройте роли (например, Developer (разработчик), Maintainer (контроль и развитие проекта), Viewer).
2. **Правила для веток**: установите ограничения для основной ветки, например, разрешить слияние только через pull request, требовать двух ревью, запрещать прямое коммитирование.

### 5. CI/CD (необязательно, но полезно)
1. **GitHub Actions**:  автоматические действия (CI/CD) для тестирования, сборки и развертывания кода. Например, можно настроить автоматическое тестирование кода перед слиянием.
2. **Проверка pull request**:  автоматическая проверка pull request на тестирование и сборку перед слиянием.

#### Пример рабочего процесса
1. **Создание ветки**: разработчик создает новую ветку для задачи.
2. **Внесение изменений**: работа ведется в ветке, коммиты фиксируют прогресс.
3. **Создание Pull Request**: по завершении задачи создается pull request для обсуждения и проверки.
4. **Code Review**: участники проверяют PR(**Pull Request**), обсуждают его, предлагают правки.
5. **Слияние ветки**: после одобрения ветка сливается в основную, задача считается выполненной.

#### Примеры инструментов на GitHub
- **Issues**: для создания задач, багов и обсуждений.
- **Projects**: для управления задачами в стиле канбан.
- **Milestones**: для отслеживания прогресса по этапам проекта.
- **Actions**: для CI/CD и автоматизации.

### 5. Наши ветки 

#### Основные правила работы с ветками

1. **Работаем в своих ветках**: каждый участник работает над задачами в своей ветке и регулярно обновляет её, чтобы избежать конфликтов.
2. **Частые коммиты**: сохраняйте прогресс регулярно, делая коммиты в своей ветке.
3. **Периодическое обновление ветки develop**: подтягивайте последние изменения из develop, чтобы ваша ветка была актуальной.
4. **Проверка перед слиянием**: перед объединением протестируйте изменения локально.
5. **Создание pull request (PR)**: завершив задачу, создайте PR из своей ветки в develop для проверки командой.

#### 2. Работа с коммитами

   - Вносите изменения в свой код и добавляйте их в коммит:
   - `git add .`: добавляет все изменённые файлы для следующего коммита.
   - `git commit -m "Описание изменений"`: создает коммит с указанным описанием.ий"`

#### 3. Синхронизация с develop

   - Чтобы избежать конфликтов, регулярно обновляйте свою ветку, подтягивая изменения из develop:
   - `git checkout develop`: переключает на ветку `develop`.
   - `git pull origin develop`: обновляет `develop` последними изменениями из удалённого репозитория.
   - `git checkout feature/user1`: переключает на ветку `feature/user1`.
   - `git merge develop`: сливает изменения из `develop` в `feature/user1`.

#### 4. Пуш изменений в удалённую ветку

   - Периодически загружайте изменения в удалённую ветку:
     - `git push origin feature/user1`: отправляет локальные изменения в удалённую ветку `feature/user1`.

#### 5. Создание Pull Request (PR)

   - Когда работа завершена, создайте pull request из вашей ветки feature/user1 в develop.
   - Сообщите команде о PR для проведения код-ревью.

#### 6. Решение конфликтов

   - Если при слиянии возникают конфликты, Git уведомит вас. Разрешите их, отредактировав конфликтующие файлы, затем:
   - `git add <имя_файла>`: добавляет файл для следующего коммита.
   - `git commit -m "Решение конфликтов"`: создает коммит с указанным сообщением.
   - `git push origin feature/user1`: отправляет изменения в удалённую ветку `feature/user1`.

#### 7. Удаление ветки после слияния

   - После успешного слияния pull request можно удалить личную ветку:
     `git branch -d feature/user1` удаляет локальную ветку feature/user1
     `git push origin --delete feature/user1` удаляет удалённую ветку feature/user1
